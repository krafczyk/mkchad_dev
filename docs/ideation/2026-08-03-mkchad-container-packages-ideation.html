Grounding

Grounding Context

The x86_64 and aarch64 definitions already provide Node 24, Python, Java, Rust, C/C++, Lua, Neovim, OpenCode, browser automation, language tooling, GitHub access, structural search, process and network diagnostics, profiling, encryption, SQLite, and media processing. Architecture parity is mechanically enforced.

OpenCode, Compound Engineering, and opencode-project-reload all use Bun for source development, but the image installs OpenCode from immutable architecture-specific release tarballs. Optional TypeScript and Bash language servers are deliberately Mason-owned. The ADR also records floating pip, npm, and source inputs, making reproducibility a stronger baseline gap than generic package breadth.

External evidence limit. Dedicated web search was unavailable in this environment. Package availability and upstream artifact claims therefore require verification before implementation.

1

Pinned Bun authoring runtime

Repository authoring toolchainsConfidence 92%Complexity Medium

Add one checksum-pinned Bun release for x86_64 and aarch64 so the container can run the documented test, typecheck, build, and validation commands in OpenCode, Compound Engineering, and opencode-project-reload. Keep Bun structurally separate from OpenCode installation: the shipped OpenCode package remains the immutable architecture-specific tarball, and structural tests continue rejecting the former source-build route.

Basis
direct: All three active TypeScript repositories declare Bun commands, while tests/nvim_container_tooling_test.sh rejects Bun-based OpenCode build remnants rather than a separately owned authoring runtime.
Rationale
This is the only absent executable tied to several current repository workflows. It also provides the in-process runtime needed if native OpenCode routing is later moved from Python to TypeScript.
Downsides
Adds another architecture-specific artifact and update policy. OpenCode and project-reload currently express different Bun versions, so one compatibility baseline must be selected and tested before pinning.
2

Freeze existing inputs before broadening the image

Baseline reproducibility and image costConfidence 88%Complexity Medium

Before adding a second convenience package, pin the existing floating Python and source selections, verify direct downloads such as Node, and capture resolved dependency closures. Evaluate uv only as a build-time mechanism after the desired Python lock and VCS-source contract is explicit.

Basis
direct: ADR 002 records pydantic@main, unpinned pip packages, mutable source branches, and uncaptured transitive package closures as current reproducibility limits.
Rationale
Stabilizing what is already shipped makes every later package proposal measurable and reviewable.
Downsides
This does not immediately add an interactive tool. uv is not yet justified as the chosen mechanism and needs upstream architecture and lock-behavior verification.
3

Conditional shfmt baseline

Repository authoring toolchainsConfidence 62%Complexity Low

Add an exact-version shfmt binary only if MkChad adopts a repository-owned formatting command or CI gate for its shell-heavy launch, lifecycle, container, and deployment code. It would complement ShellCheck rather than duplicate a language server.

Basis
reasoned: The image already validates ShellCheck and the workspace maintains many shell scripts, but no current workflow invokes shfmt.
Rationale
A formatter can make a broad shell surface cheaper to maintain, but only when its formatting contract is explicit.
Downsides
Without an adopted gate this is merely a familiar convenience and should not enter the baseline.
4

Navigation admission freeze

Editor and shell navigationConfidence 94%Complexity Low

Explicitly decline fd, fzf, bat, zoxide, and terminal-multiplexer additions until an exercised MkChad workflow identifies an operation not covered by Snacks, ripgrep, ast-grep, OpenCode fuzzy matching, or native terminal providers.

Basis
direct: Current picker, text-search, structural-search, and terminal paths are already owned by MkChad, OpenCode, or Neovim integrations.
Rationale
This keeps personal shell preference separate from the immutable product baseline.
Downsides
Users who prefer those commands must install them in a writable user layer or use host tools.
5

Host-side dependency closure artifacts

Diagnostics and release operationsConfidence 86%Complexity Medium

Generate RPM, pip, npm, Cargo, LuaRocks, and source-revision inventories beside each released image. If an SBOM tool such as syft is selected, keep it pinned in release CI or on the build host rather than shipping it inside the interactive container.

Basis
direct: ADR 002 already says resolved package lists should be captured when exact image provenance is required.
Rationale
The next diagnostic tool should explain the entire image rather than become one more unexplained image component.
Downsides
This improves release evidence but does not add an in-container capability. Tool selection remains unverified externally.
6

Close release architecture parity first

Diagnostics and release operationsConfidence 95%Complexity Medium

Require both x86_64 and aarch64 verified SIF artifacts before calling a release parity-complete. The source definitions maintain package parity, but the current parent release manifest binds only an x86_64 image.

Basis
direct: deploy/release.json currently contains one x86_64 artifact despite architecture-aware deployment code and parity-tested source definitions.
Rationale
Adding packages to both Dockerfiles has limited value if only one resulting architecture is distributable through the release contract.
Downsides
This expands build and release operations rather than the package baseline itself.
